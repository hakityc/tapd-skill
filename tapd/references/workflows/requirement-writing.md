# 需求写法

生成、整理或精简需求正文与发布预览时使用；用户指定其他格式时优先遵循。

## 写作规则

- 说人话，直接写谁遇到什么问题、要改成什么、有什么用。每段通常 1–2 句，避免套话、重复和无关技术细节。
- 验收只抓本期交付的核心结果，通常 1–3 条，写清用户能看到或验证的行为。不按按钮、字段、接口或测试步骤逐项展开，也不为凑满 3 条补内容；必要的细节留在产品规格、任务或测试用例中。
- 简单需求将目标与验收合为一段；确需分点时，只在「目标与验收」下列核心条目。复杂需求先合并同类结果，仍不足以表达时可超过 3 条或建议拆分，不遗漏关键业务约束。
- 范围写清本期做什么、相关但不做什么；有已明确的子任务时，在范围后加一行「子任务：……」，不为填模板自动拆任务或创建工作项。
- 只写用户输入或文档支持的事实，不自定上线版本、日期、指标或承诺。上线未明确写「待定」；风险未明确写「待确认」，已确认无风险才写「无」。示例里的 rev30 只属于该示例。
- 精简已有需求时保留原意与关键约束；只要求精简某一部分时只改该部分。写入已有需求前先回读，Flow 受管区块按 `references/tapd/spec-publisher.md` 更新。

## 默认格式

使用加粗的中文方括号标签，段间空一行，不再追加重复的「详细需求」「验收标准」或总结章节。

```markdown
**【背景】**谁遇到了什么问题，当前有什么不便。

**【目标与验收】**本期改成什么样，怎样确认核心功能可用。

**【价值】**解决后，用户或业务能得到什么。

**【范围】**本期做什么；相关但不做什么。
子任务：已明确的子任务；没有则省略此行。

**【上线】**已明确的环境、版本或时间；未明确写「待定」。

**【风险】**已知风险；未明确写「待确认」，已确认无风险写「无」。
```

## 示例

**【背景】**用户反馈工作事项列表最新截止的事项排在最底部，希望截止时间能自己切换顺序或倒序；列表越来越长，要一直往下拉。

**【目标与验收】**工作事项列表可按截止时间切换升降序，分组可折叠，长列表滚动时表头与组头吸顶；上线生产 rev30。

**【价值】**最近的事项一眼可见，长列表不用反复下拉找表头。

**【范围】**本期工作事项列表的排序、折叠与吸顶；概览重点事项、CLI、插件、导出不变。
子任务：工作事项列表截止时间排序与分组折叠。

**【上线】**生产 rev30。

**【风险】**无
